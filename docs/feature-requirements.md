## 一、核心文档：新功能需求与系统设计文档

三个特性之间存在依赖关系：多数据库工厂是地基（健康检测的读写探针、版本清单里的 DB_SCHEMA_VERSION 都依赖统一的数据库抽象），版本控制是纽带（健康检测的「客户端连通状态」直接消费版本握手的产物）。建议按文档内实施顺序推进。

### 1. 核心功能需求定义 (Core Requirements)

#### 1.1 前端/脚本 JS 版本控制与面板一致性比对 (JS Version Control & Diagnostics)

##### 1.1.1 现状与问题

| 环节 | 现状 | 问题 |
|---|---|---|
| 版本事实来源 | 仅 package.json 有 1.0.1 版本号，未注入任何运行产物 | 各组件无版本常量，无法比对；Surge 脚本内仅 BUFFER_VERSION 这类数据格式版本，与脚本版本无关 |
| 网页 ESM | Cloudflare Pages 静态资源按内容缓存；面板 API 的 GET 请求已有缓存击穿参数 | 静态资源层无版本参数化：index.html 与入口脚本引用不带版本，PWA 的 sw.js 缓存与页面可能半新半旧 |
| Surge 远程脚本 | .sgmodule 的 script-path 固定指向 raw.githubusercontent.com 的 main 分支 | GitHub raw 自带约五分钟边缘缓存，且 Surge 拉取时机不可控，更新后客户端可能长期拿旧文件 |
| 捕获脚本 | 规则脚本只支持本地文件，用户从模板 final-logger-src 另存为本地副本 | 部署后永不自动更新，版本漂移是必然事件，且目前没有任何手段发现漂移 |
| 比对机制 | 无 | 服务端不知道客户端在跑什么版本，客户端也不知道服务端最新版本 |

##### 1.1.2 版本号规范与唯一事实来源

- 主版本源：package.json 的 version 字段为语义化版本（X.Y.Z），构建期附加 git 短哈希与构建时间，合成「构建清单」这一唯一事实来源；展示形式为 X.Y.Z（短哈希）。
- 注入面（构建期一次性完成，见 2.1 流程）：

| 产物 | 注入方式 | 版本展示位置 |
|---|---|---|
| 后端 Worker | 构建脚本将版本常量写入打包产物 | /api/meta 响应（serverVersion 字段） |
| 前端 ESM | 构建生成独立的 version.js 常量模块，config.js 引用 | 设置页版本看板、页面横幅 |
| final-panel.js | 文件头版本常量 + #!desc 文案追加版本号 | Surge 面板正文、脚本编辑器 |
| final-logger.js | 文件头版本常量 | 上报请求捎带 + Surge 持久化键 |
| final.sgmodule | 模块头注释版本号 + script-path 查询参数 | Surge 模块列表、直装页 |
| sw.js | 缓存命名空间附带版本串 | 更新时整体清除旧缓存（对用户不可见） |

- 版本演进规则：

| 变更类型 | 版本动作 | 原因 |
|---|---|---|
| 上报协议、final_db_config 持久化键结构 | 次版本必须递增 | 跨次版本视为协议变更，触发面板的「严重落后」判定 |
| 面板 UI、导出格式、查询参数 | 补丁版本 | 仅影响展示与便利性 |
| 数据库表结构 | DB_SCHEMA_VERSION 独立递增 | 与 JS 版本解耦，参与健康检测而非版本看板 |

- DB_SCHEMA_VERSION 独立管理：当前迁移机制是列探测加 ALTER TABLE，无版本号可读；多数据库工厂落地时引入版本表（见 1.3），此后 meta 返回值携带该版本，供健康检测的 Schema 一致性检查使用。

##### 1.1.3 缓存破坏策略（按分发通道分治）

| 通道 | 策略 | 失效时机 |
|---|---|---|
| index.html（引用源） | 响应头 no-store 或极短 max-age | 每次访问都新鲜，保证入口引用的版本参数是最新的 |
| ESM 模块 | index.html 引用入口 main.js 时附带查询参数版本号；模块之间的相对导入不带参数，整张模块图随入口参数一起失效 | 发版即失效；浏览器对同参数请求命中缓存 |
| sw.js（PWA） | 缓存命名空间带版本串；检测到新版本时旧缓存整体清除、新 SW 立即接管 | 发版后首次访问 |
| 面板 API GET | 维持现有 public, max-age=30/60 不变 | 已有击穿参数，不动 |
| /api/meta | 强制 no-store | 版本比对基准绝不能被边缘缓存 |
| Surge 远程脚本 script-path | URL 追加查询参数版本号；发版时 sgmodule 与脚本同一 commit 更新参数，Surge 重新拉模块时连带重新拉脚本 | 发版即失效 |
| 捕获脚本本地副本 | 无法自动失效，闭环止于「发现并提示」：靠 1.1.4 的上报捎带比对 | 用户按面板指引重新另存 |
| .sgmodule 直装链接 | 中期方案：Surge 三件套（模块与两个脚本）改由自家 Pages 域名托管（静态目录随 dist 发布或 Worker 路由），缓存头完全可控，版本参数与 max-age 双保险 | 发版即失效；同时解决 GitHub raw 的边缘缓存延迟与国内可达性问题 |

##### 1.1.4 服务端/客户端版本握手校验

- 服务端单一出口：扩展现有 /api/meta（前端启动已在调用，无新增请求成本），响应追加版本清单对象，包含 serverVersion（后端构建版本）、components（panel 脚本、logger 脚本、sgmodule 各自的最新版本，来源为构建清单）、dbSchemaVersion。响应头 no-store。
- 三类客户端的握手方式：

| 客户端 | 握手通道 | 比对对象 | 落后时的动作 |
|---|---|---|---|
| 网页前端 | 启动时请求 /api/meta（既有调用，零新增请求） | 自身 version.js 常量 对 serverVersion | 渲染顶部横幅；PWA 场景联动 sw.js 更新流程 |
| final-panel.js | 每次面板刷新的既有数据请求响应中捎带 latest 字段 | 自身文件头 SCRIPT_VERSION | 写入 Surge 持久化并在面板渲染提示 |
| final-logger.js（本地副本） | 批量上报的响应体捎带 latestLoggerVersion（零额外请求） | 自身文件头版本 | 写入持久化键 final_db_config，由面板读取展示（本地副本无法自更新，闭环止于提示） |

- 判定分级：一致（绿）、小版本落后（黄，建议更新）、大版本落后（红，上报协议可能不兼容）、客户端领先（蓝，服务端待部署——自托管用户更新网页代码前常见）。
- 兼容性承诺：后端兼容往前一个大版本的上报格式；meta 与捎带字段只增不删，旧客户端忽略未知字段不受影响。

##### 1.1.5 Panel 版本看板 UI 与警示策略

- 位置：设置页新增「版本与更新」卡片；首页顶部状态条放一个精简版入口（仅显示是否有落后项）。
- 看板列：组件名、客户端当前版本、服务端最新版本、分发通道（网页内置 / 远程脚本 / 本地副本 / 模块外链）、状态徽标、捕获脚本最近上报时间。
- 徽标配色沿用 Bootstrap 语义色（success / warning / danger / info），与现有策略徽标的配色体系一致。
- 警示策略：

| 状态 | 呈现 | 附加动作 |
|---|---|---|
| 普通落后（黄） | 看板行黄色徽标 + 一句话更新指引，链接 readme 对应章节 | 无 |
| 严重落后（红，跨大版本） | 页面顶部红色横幅常驻，说明风险（上报可能被后端拒绝、统计可能失真） | 捕获脚本可选自动降级为停止上报（开关持久化于 final_db_config，防脏数据） |
| 捕获脚本落后 | 面板与网页端同时提示 | 给出「重新另存本地脚本」的分步指引（复用现有教程锚点） |
| 网页自身落后 | 顶部横幅「发现新版本，点击刷新」 | 点击触发 SW 更新并重载 |
| 服务端落后（客户端领先，蓝） | 看板行蓝色徽标 | 提示更新服务端部署 |

#### 1.2 一键部署与权限检测系统 (Deployment Health Check System)

##### 1.2.1 目标与设计原则

- 目标：新用户部署完成后五分钟内自证整套链路（浏览器 → Pages → 数据库 → Surge 客户端）已通；老用户排查配置漂移与令牌轮换事故。
- 原则：只读检查默认执行；涉及写、删的探针必须用户主动触发（深度检测）；诊断结果一律脱敏；健康端点不新增任何特权，全部检查走既有鉴权体系。

##### 1.2.2 检测项清单

| 编号 | 检测项 | 检查内容 | 深度检测 | 失败时报告内容 |
|---|---|---|---|---|
| 1 | 配置完整性 | 环境变量在位性与格式：TURSO_API_URL（https 协议校验，复用 getTursoConfig 既有规则）、TURSO_AUTH_TOKEN、PANEL_WRITE_TOKEN、PANEL_HIT_TOKEN | 否 | 缺哪个变量、格式错在哪；写令牌未配置降级为警告（写接口开放但有 Warning 头），上报令牌未配置为错误（上报接口一律拒绝） |
| 2 | 数据库连通性 | 适配器 ping（对库发一条最轻探测语句） | 否 | 区分超时 / 拒绝 / 地址不可达三类，附归一化错误说明 |
| 3 | Schema 一致性 | LOGS 表存在、必需列齐全、DB_SCHEMA_VERSION 与代码期望对齐 | 否 | 缺表 / 缺列 / 版本不匹配，附迁移指引 |
| 4 | 读权限 | 对 surge_logs 真实读取一行 | 否 | 读失败的具体错误归类 |
| 5 | 写权限 | 向独立的 health_probe 表写入一行带唯一标记的临时数据 | 是 | 写失败归类（权限 / 配额 / 锁冲突） |
| 6 | 读回校验 | 按唯一标记读回探针行并比对内容 | 是 | 不一致说明写入不可靠 |
| 7 | 删除权限 | 删除探针行并核对受影响行数为一（复用 statementChanges 的既有归一语义） | 是 | 删除失败说明账号无写权限或只读 |
| 8 | 写令牌校验 | 带正确令牌调用轻量鉴权探针（不落库）；可选反例：错误令牌应被拒绝 | 是 | 令牌不匹配 / 未配置，提示到面板「写接口令牌」处修正 |
| 9 | 上报令牌校验 | PANEL_HIT_TOKEN 在位性；深度模式下模拟一次带令牌的合法探测上报 | 在位性否，模拟是 | 未配置 / 不匹配，提示与 Surge 模块参数 FINAL_DB_TOKEN 核对 |
| 10 | 客户端连通状态 | 读取最近一次 final-panel 心跳（见 1.2.4） | 否 | 在线 / 离线 / 客户端版本落后（与 1.1 联动） |
| 11 | 外部依赖（可选扩展） | Gist 备份令牌、订阅源可达性 | 是 | 保留为扩展项，短超时、默认跳过 |

- 第 5–7 项的三步必须在同一个批量事务内完成（Turso 走 executeTursoBatch 的既有原子性），失败自动回滚，任何情况下不留残留数据。

##### 1.2.3 后端管道设计（/api/health）

- 路由归属：挂在 /api 前缀下，_routes.json 已覆盖全部 /api 路径，无路由配置改动。
- 两级模式：mode=basic（编号 1–4、8 与 9 的在位性、10，全部只读）与 mode=deep（编号 5–9 全量，前端二次确认后触发，建议要求携带写令牌）。
- 响应结构（文字描述）：逐项给出检查名、状态（pass / warn / fail / skip）、耗时毫秒、人类可读说明、修复建议、readme 文档锚点；末尾附汇总结论与最关键失败项。
- 错误归类沿用 ConfigError（配置问题，400 语义）体系，运行时错误归为连接类、权限类、数据类，报告里分开呈现，避免「数据库连不上」和「令牌填错」混为一谈。
- 安全约束：健康端点永不回传令牌值与完整数据库地址，只回主机名（复用 redactUrl 的既有语义）；深度检测有服务端节流（见优化建议 2）。
- CORS：同源部署（现状）无预检问题；自定义域名跨域场景下，健康接口显式应答 OPTIONS 预检，仅放行面板自身来源，不使用通配符。

##### 1.2.4 客户端探测机制（配合 final-panel.js）

- 方案取「零新增配置」：final-panel.js 每次刷新面板时，把心跳捎带给后端——客户端标识（首次生成随机标识并持久化于 final_db_config，不采集个人信息）、自身脚本版本、刷新时间。后端写入既有 prefs 存储或独立客户端注册表。
- 网页端健康页读取最近心跳，展示最近在线时间、客户端版本、版本比对结果，与 1.1 的版本看板共用数据。
- 离线判定阈值：两个刷新周期内无心跳视为离线（默认刷新间隔 600 秒，即约 20 分钟无心跳）。
- 鉴权：心跳走上报令牌体系（与面板数据请求同一鉴权面，PANEL_HIT_TOKEN），不新增令牌类型，不新增 Surge 侧配置负担。

##### 1.2.5 前端入口与 UI 设计

- 导航入口：nav.js 的页面清单新增「配置检测」项（第五位，图标建议 🩺），顶部导航与底部 TabBar 自动一致（nav.js 双渲染是现成能力，无需额外适配）。
- 视图结构：顶部「开始检测」与「深度检测」两个按钮；中部为检测项清单（逐项状态图标、耗时、说明）；底部为汇总结论卡。
- 交互细节：
  - 轻量化取舍：一次请求返回全部结果，前端按序动画展示（不做逐项轮询，避免多次往返）。
  - 失败项可展开，显示修复建议与 readme 锚点。
  - 「复制诊断报告」按钮：生成纯文本、已脱敏的报告，便于贴到 issue 求助。
  - 深度检测需二次确认（弹窗说明将写入临时数据并立即删除）。
- Bootstrap 组件映射：检测项用 list-group，状态用徽标与 alert 变体，确认框用 modal，与现有面板组件风格一致。

#### 1.3 多数据库工厂架构设计 (Multi-Database Factory Pattern)

##### 1.3.1 现状与问题

- turso.js 是唯一数据访问出口：配置解析（getTursoConfig / resolveTursoConfig）、SQL 执行（executeTurso / executeTursoBatch）、变更行数归一（statementChanges）。
- 所有业务模块（logs/ 下的九个文件、prefs.js、subscriptions.js）直接 import 执行函数并手写 SQL。
- Turso 专属语义已渗漏到业务层：serializable 事务假设、rows_written 返回形状、HTTPS 超时常量、libSQL 错误文案正则（迁移里的 duplicate column name 判断）。
- 迁移机制与 Turso 强耦合：列探测加 ALTER TABLE，且 migrationsApplied 只是 isolate 内布尔量（架构审查已指出冷启动竞态）。
- 后果：更换数据库等于全量重写数据层；e2e 测试用 node:sqlite mock 反向模拟 Turso HTTP 响应形状，测试与生产不同路径。

##### 1.3.2 抽象层接口（DatabaseAdapter）规范

- 设计取舍论证：
  - 方案 A（通用执行器）：仅把 executeTurso / executeTursoBatch 换签名替换。迁移成本最低，但事务语义差异会以运行时数据不一致的形式爆雷——Turso 的批量是「单事务、失败回滚」，D1 的 batch 是「原子但无跨批事务」，业务层里「删除加新增必须同事务」的成对操作假设会悄悄失效。
  - 方案 B（领域仓储）：每个后端实现全部领域方法。接口面太大，约束业务表达力，迁移工作量也大。
  - 推荐折中（方案 A 强化）：接口核心是「批量语句组」这一原子单元，外加少量领域方法；语义契约（原子性边界、变更行数、错误归类）由适配器负责，业务层只声明意图不关心方言。
- 接口方法清单：

| 方法 | 职责 | 语义契约 | Turso 实现 | D1 实现要点 |
|---|---|---|---|---|
| init(env) | 解析配置或平台绑定，格式校验 | 缺配置抛 ConfigError（路由 400 语义不变） | 沿用 getTursoConfig | 读取 D1 绑定对象，无需地址令牌 |
| ping() | 连通性探测 | 超时自控、失败归类 | 一条轻量语句 | 同 |
| getSchemaVersion / ensureSchema | 版本读取与幂等迁移 | 以版本表为准，天然幂等，替代列探测 | 建版本表 + 版本号推进 | 同，DDL 语法差异内聚 |
| executeBatch(statements) | 原子语句组 | 组内要么全成功要么全回滚 | 既有批量事务（serializable） | batch 原子性；跨组事务不可用，领域方法必须单批完成成对操作 |
| changes(result) | 变更行数归一 | 统一数字返回 | rows_written / affected_row_count 双形状 | meta.changes 形状 |
| upsertHits（领域方法） | 批量命中合并写入 | 窗口合并、单事务 | 方案（架构审查建议）落地于此 | 可用 RETURNING 省一次往返 |
| listLogs / getStats / exportRows | 查询域 | 分页、筛选语义与现状一致 | 组合 executeBatch | 同 |
| upsertRules / deleteRules | 规则写域 | 成对操作单事务 | 组合 executeBatch | 单 batch 完成 |
| prefs 读写 / subscriptions 读写 | 偏好与订阅域 | 键值语义不变 | 组合 executeBatch | 同 |

- 错误模型：ConfigError 保留（配置错误，400）；新增统一的运行时错误归类（连接类、语法类、约束类、超时类），业务层只判断类别不看品牌，Turso 的错误文案正则全部收进适配器。

##### 1.3.3 工厂类（DatabaseFactory）实现机制

- 选择变量：环境变量 DB_BACKEND，合法值 turso / d1 / sqlite；未配置时默认 turso——零配置兼容所有现有部署，行为与当前完全一致。
- 各后端的解析来源：

| DB_BACKEND | 配置来源 | 必需项 | 适用场景 |
|---|---|---|---|
| turso（默认） | TURSO_API_URL + TURSO_AUTH_TOKEN | 两者 | 现有部署，零改动 |
| d1 | Cloudflare Pages 平台绑定（env 中的 D1 绑定） | 绑定 | 想留在 Cloudflare 生态、免外部服务与配额双算的用户 |
| sqlite | 环境变量指定本地库文件路径 | 路径 | 自托管 Node 场景；e2e 测试的真实后端 |

- 生命周期：业务路由统一经 factory.get(env) 取适配器；isolate 内缓存实例（配置在请求间不可变）；惰性初始化，首次使用才校验配置。
- 失败语义：工厂不吞错——缺配置立即返回 400 响应（沿用 resolveTursoConfig 的既有交互模式）；DB_BACKEND 填了非法值同样 400 并列出合法值清单。
- 各适配器实现要点：

| 适配器 | 传输 | 事务能力 | 超时与重试 | 风险与对策 |
|---|---|---|---|---|
| TursoAdapter | HTTPS API（现状封装） | 批量单事务、serializable、失败回滚 | 保留 10 秒超时常量 | 远端写放大（架构审查已述），由 upsertHits 领域方法做窗口合并 |
| D1Adapter | 同账号平台绑定调用 | batch 原子、无跨批事务、无 serializable | 平台托管，无配置项 | 成对操作必须单批完成；libSQL 方言差异（占位符、UPSERT、内置函数）在适配器内归一 |
| SqliteAdapter | 本地文件（node:sqlite） | 真事务、完整隔离 | 无网络超时 | 仅自托管；e2e 从「mock 模拟 Turso」升级为「真实适配器」，测试与生产同路径 |

- 明确不做（轻量化边界）：不做跨库自动数据搬迁（切换数据库属运维操作，走既有导出与未来导入路径）；不做多库并存双写；/api/logger/schema 等既有端点对外语义不变。

### 2. 系统关键流程与交互设计 (Key Workflows)

#### 2.1 版本比对数据流

**阶段一：发布流水线（构建期，一次性）**

| 步骤 | 参与方 | 动作 | 产物 |
|---|---|---|---|
| 1 | 构建脚本 | 读取 package.json 版本 + git 短哈希 + 构建时间 | 构建清单 |
| 2 | 构建脚本 | 向五处产物注入版本（后端常量、version.js、两个 Surge 脚本头、sgmodule 参数与 script-path 查询参数） | 全组件带版本 |
| 3 | 开发者 | sgmodule 与脚本在同一 commit 提交（原子发布，杜绝「半更新窗口」） | 一致的仓库状态 |
| 4 | 部署 | wrangler 部署 Pages，静态资源随部署天然失效 | 服务端就绪 |

**阶段二：服务端汇总**——/api/meta（no-store）返回 serverVersion、components 清单（panel 脚本 / logger 脚本 / sgmodule 的最新版本）与 dbSchemaVersion，作为唯一比对基准。

**阶段三：网页前端**——用户打开面板，index.html 以带版本参数的 URL 加载 main.js；启动时的既有 meta 请求带回版本清单；前端比对自身 version.js 常量，落后则渲染顶部横幅并联动 sw.js 更新；设置页版本看板渲染完整比对矩阵。

**阶段四：Surge 面板脚本**——final-panel.js 每次刷新发起的既有数据请求，响应捎带 latest 字段；脚本比对自身 SCRIPT_VERSION，落后则写入 Surge 持久化并在面板正文渲染版本行与更新提示。

**阶段五：捕获脚本（本地副本）**——final-logger.js 每次批量上报的响应体捎带 latestLoggerVersion；脚本比对自身版本后写入 final_db_config 持久化；面板下次刷新读取该键，在看板中把捕获脚本标为「落后」并给出重新另存的分步指引。本地副本无法自更新，闭环止于提示，这是规则脚本仅支持本地文件的平台约束决定的。

**阶段六：心跳旁路**——面板刷新同时上报客户端标识与版本（与 1.2.4 共用通道），服务端由此可观察全网客户端的版本分布，为后续「强制最低版本」决策提供依据。

## 二、优化建议 (Optimization Suggestions)

以下建议独立于核心设计文档，供后续迭代参考。

**1. CDN 边缘缓存自动失效要「分层信任」，meta 绝对不可缓存。**
静态资源依靠「部署即失效」的 Pages 特性 + 入口 HTML 的 no-store 即可，不需要为每个模块文件做内容哈希重命名（构建复杂度不划算）。关键是 /api/meta 与 Surge 脚本托管响应必须绕过边缘缓存或使用极短 TTL，否则版本比对基准被边缘节点缓存后会出现「明明发版了，全网客户端都以为自己是最新的」的假阴性。Surge 三件套收编到自家域名后，用 max-age 与版本参数双保险：参数保证发版即失效，max-age 兜底防抖。发布侧坚持「sgmodule 与脚本同一 commit」的原子性，避免 raw 源与自托管源并存时的半更新窗口。

**2. 客户端探测要防打扰，更要防滥用。**
心跳搭车面板既有刷新（不新增定时器、不新增请求），本身就是天然节流。深度检测是唯一有写副作用的入口，必须服务端节流：按来源 IP 加时间窗（例如每分钟至多一次），写探针固定写独立 health_probe 表而非业务表，防止探针数据污染统计与导出。诊断报告在生成侧就完成脱敏（主机名、令牌、IP、订阅地址、数据库地址只留主机名），不要依赖用户手动删减——泄露往往发生在「复制粘贴求助」这一步。

**3. 适配器扩展性靠「语义契约 + 契约测试」，不靠提前抽象。**
接口面保持最小（1.3.2 清单），每个方法用注释写死语义契约（原子性边界、变更行数含义、错误归类），新增后端时先读契约再实现。真正的准入门槛是契约测试套件：把现有 e2e 的断言重组为「同一组断言跑全部适配器」（turso mock、D1 本地模拟、node:sqlite 真实库），任何新适配器（Upstash、Supabase 等）通过全部契约断言才算接入。约束 Turso 的错误文案与形状绝不上抛到业务层——这既保护业务代码，也让换后端时的排查范围限定在适配器内部。

**4. 版本判定的数据可信度：以服务端部署为准，容忍客户端领先。**
GitHub raw 有约五分钟边缘缓存且国内可达性不稳定，自托管双源初期可能出现「raw 上还是旧版、自家域名已新版」的分裂；版本比对的唯一基准必须是 /api/meta 返回的部署版本，而不是任何外部源。客户端版本领先时只显示蓝色提示、不做任何阻塞或降级——自托管用户「先更新网页、后部署后端」是正常操作，把领先当错误会造成误报循环。版本清单字段只增不删，老客户端忽略未知字段的既有行为是向后兼容的根基，改字段前先想兼容窗口。

**5. PWA 与 ESM 模块图的更新编排要「整体切换」，防半新半旧。**
原生 ESM 按文件 URL 缓存，模块图里只要有一个文件新旧不一致，就可能出现「新 UI 配旧逻辑」的诡异状态。入口参数版本化让整张模块图随一个参数一起失效，sw.js 的缓存命名空间也要带同一版本串：新 SW 接管后清掉全部旧缓存再放行页面，两套缓存（HTTP 缓存与 SW 缓存）由同一版本源驱动，才不会互相打架。刷新提示的时机放在 SW 接管完成之后，避免用户点击刷新后拿到的仍是旧缓存。
