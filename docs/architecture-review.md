## 一、核心文档：项目全面审查与修复建议文档

### 1. 架构与隐患审查

#### 1.1 Serverless 与数据库交互（CF Pages Functions 到 Turso）

##### 冷启动与请求延迟

当前每一次对 /api/logger 前缀的请求，在真正执行业务 SQL 之前都要先跑 ensureMigrations，而迁移本身是一条独立的 ALTER TABLE 远端写操作。也就是说冷 isolate 的首请求是「配置解析、迁移往返、业务往返」两次串行 TLS 往返，且第一次还是一次 schema 变更。

migrationsApplied 是模块级布尔量，只在单个 isolate 内生效。Cloudflare 在负载上升时会并发拉起多个 isolate，每个 isolate 都会各自执行一次这条 ALTER TABLE。libSQL 的 schema 变更需要写锁，冷启动突发时这些迁移语句会与正常的命中写入互相争锁，把本该是一次性开销的迁移放大成周期性的写锁抖动。

##### 批量处理与连接模型

executeTursoBatch 的设计是正确的：一次 POST、一个远端事务、serializable 标志、失败自动回滚。这是本项目在 Turso HTTP 协议下能做的最优形态，问题不在它本身，而在谁在用。

最高频的 recordHit 只提交一条语句。等于用批量事务的完整代价（TLS 握手、事务协商、回滚日志）去换一条单行 upsert。批量机制已经建好，但唯一需要它的路径没有接入。

另外，Turso 侧失败没有任何客户端重试。fetch 抛错、超时或返回 5xx 时，异常直接穿透到 errorResponse 变成 500，上报就此丢失。整个系统唯一的数据入口是 at-most-once 语义，没有任何补偿机制。

##### 高频命中采集对配额与并发的影响

这是架构层面最重的隐患，由三个因素叠加而成：

1. 客户端零合并：final-logger.js 在每条 FINAL 匹配上各触发一次，脚本内没有「最近已上报过这个主机名」的内存去重，也没有窗口聚合。
2. 服务端零缓冲：/api/logger/hit 是单条落库接口，没有批量入口，没有队列，没有合并窗口。
3. 计数写放大：count = count + 1 无条件累加，且 policy 被每次命中无条件覆盖。

FINAL 是规则链末端，命中面极大。三者叠加的后果是 Turso 的写 QPS 与「未命中任何规则的流量」成正比，而不是与「不同主机名数量」成正比。免费档还有 Worker 自身的每日请求上限，属于第二道墙。

更深一层的数据质量问题：count 实际度量的是「脚本执行次数」而非「有效命中次数」。单个高频主机名可以把 count 推到很高，永久性地扭曲所有依赖 min-count 的导出筛选，而且这个扭曲事后无法还原。

##### SQL 注入与参数绑定

逐处核对 SQL 构造点后，结论是没有注入面：

- 所有用户值一律走占位符绑定，包括 LIKE 模式；likeEscape 对百分号、下划线、反斜杠做了转义，且与 SQL 侧的 ESCAPE 子句配套使用，没有只做一半的情况。
- 表名与列名（LOGS_TABLE、WRITE_COLUMNS、LOG_COLUMNS、RULE_COLUMNS）全部是编译期常量，不来自请求。
- 订阅地址、user 标识、参数文本都经过归一化后再进入绑定。

这一块是项目里做得最扎实的部分。

##### 事务控制与原子性

单次 executeTursoBatch 内部是原子的，跨批次的都不是。三处真实存在问题：

1. batchOverride 分块顺序提交：flushChunks 按 BATCH_CHUNK_SIZE 切块，每块一个独立事务。第 3 块失败时，第 1、2 块已经提交。大批量粘贴导入失败后会留下「导入了一半」的状态，且没有幂等标识可用于安全重入。
2. reduceExclude 的降维排除：删除语句被切成最多 200 条一块，汇总行挂在最后一块。中途失败的结果是「受害记录已删，汇总行没插入」，这是真正的数据丢失且不可回滚。
3. reduceExclude 的读写分离：受害行是先在一次全表 SELECT 里读出来的，删除发生在后续的另一个事务里。两者之间存在窗口，期间一次并发命中会把某个受害主机名重新插回来。结果是汇总 count 少算，同时库里留下一条汇集范围之外的多余行。

preserveEditedRow 到 renameLog 再到 flushChunks 也是同一条链上的三个独立事务，共享同一个不一致窗口。

##### SPOF 归纳

单一 Turso 实例同时承担读与写，无只读副本、无多库、无降级路径。它是整个系统唯一的硬单点：数据库不可用时，上报、面板、导出、订阅直链会同时失效。

#### 1.2 前端与数据同步（原生 ESM 与 Bootstrap）

##### UI 与数据是否失步

「写后必须手动刷新网页」这个经典问题已经被处理了：cpRequest 对 GET 统一加 _cb 时间戳击穿 Cache-Control public max-age=30，写操作之后也都走 cpRefreshAll。所以不存在用户可见的持久失步。

但代价是刷新模型为「全量重来」。任何一次写操作（删除、降维、批量覆盖、清空）之后：

- 并发 4 个请求：list、stats、meta、allLogs；
- 其中 list 与 allLogs 各自拉取最多 5000 行全列数据；
- 只为了更新 6 个统计卡和一张表。

一次降维操作的净成本是 4 次往返加约 10000 行 JSON。

##### 冗余拉取与线性扫描

cpLoadAllLogs 的存在理由只是填充来源下拉框和做 hostname 反查，它把列表数据拉了第二遍。而 state.allLogs 被三处线性扫描：

- openQuickEdit 用 find 定位行；
- fillQuickEditDatalists 遍历收集所有出现过的策略名；
- cpMatchedBy 在 renderQuickLevels 里对每一个降维候选都完整遍历一次 allLogs。

第三处是候选数乘以全量行数，且发生在每次打开编辑弹窗时。候选通常有 3 到 5 个，全量 5000 行时就是一万五到两万次比较，只为显示「匹配 N 条记录」。

##### 大批量渲染性能

实际渲染策略比预期健康：renderLogList 用字符串拼接加一次 innerHTML，而每页只有 20、50、100 三档。这个选择是对的，全量重绘在小页尺寸下比逐行 diff 更快。

真正的成本在上游而不在 DOM：

- 页面始终最多拉 5000 行进内存；
- cpVisibleLogs 在每次搜索防抖触发、每次筛选切换、每次排序切换时都对这 5000 行重新过滤并排序；
- 服务端本来就支持 search、policy、type 条件下推，但来源筛选和自由文本搜索仍在前端对全量数组二次过滤。等于数据库的索引工作被浪费，前端又重做一遍。

超过约两万行之后，没有虚拟滚动、没有分页下推的代价会开始显现在交互延迟上。

##### 并发与状态竞态

state.busy 是逐函数检查的，cpRefreshAll 自身没有守卫。两次刷新交叠时，先发的请求可能后到，把旧数据渲染上去。savePref 与 cpRefreshAll 之间也没有 await 排序保证。表现为偶发的「刚删完又看到那条规则」。

##### XSS 防护

转义纪律全文一致，cpEscape、cpAttr、cpOnQuote 各司其职，没有发现绕过点。尤其是 cpOnQuote 的注释点出了 HTML 实体在内联 onclick 里不够用、必须用 Unicode 转义替换单引号的原因，这说明作者是真的被这类问题咬过。前端这块没有安全问题。

#### 1.3 Surge 客户端与脚本层（.sgmodule 与本地脚本）

##### 超时机制对链路延迟的影响

final-logger.js 的 post 设了 5 秒超时。这是一条会拖慢代理链路的值：Worker 冷启动要做迁移往返加业务往返，两次串行 TLS 之后 5 秒并非不可能耗尽。一旦耗尽，脚本阻塞到超时才结束，而服务端的写可能仍然成功，客户端已经视为失败并记录了错误日志。

final-panel.js 的 get 没有显式超时，只依赖 .sgmodule 里 Script 行的 15 秒。面板脚本比上报脚本宽松得多，两者策略不一致。

##### 来源追踪的参数传递可靠性

配置走的是两跳链：模块 argument 到面板脚本，再到 persistentStore 键 final_db_config，最后到捕获脚本。这条链有几个真实的可靠性缺口：

1. 强依赖面板先刷新一次。若用户装了模块但没等到面板刷新，或 persistentStore 写入失败，捕获脚本会无限期静默跳过上报，且没有任何提示。
2. 存储的 JSON 没有版本号与校验。半写入或旧格式的配置与合法配置无法区分，脚本只会按「读到了就用」处理。
3. 令牌被持久化到设备。上报令牌随配置一起写进 persistentStore，而这是其他脚本也能读的共享存储。令牌作用域仅限 hit 接口，爆炸半径有限，但仍是客户端的一份静态凭据。

多设备追踪本身也偏弱：来源取 environment 的 device-model，同型号的多台设备会合并成同一个来源；同时所有设备共享同一份 final_db_config，策略名是全局单值而非每设备独立。所以「多设备来源追踪」实际达成的是「多机型追踪」。

另外 params 恒定为空串上报，Surge 不向规则脚本暴露 no-resolve 等参数，所以真实命中永远采集不到参数，只有手工编辑和批量导入能写入参数。

##### 客户端自身的性能问题

面板脚本为了算 6 个统计数字，拉取了 /api/logger 的完整列表（默认 5000 行、10 列）。项目里已经有现成的 /api/logger/stats 端点，一次批量 10 条聚合语句就能给出同样的数字。在手机蜂窝网络下，这是为一个简单渲染付出了几百倍的有效载荷。

##### 逻辑重复

主机名类型推断有三份独立实现：Surge 脚本里的 inferTypeFromHost、后端的 inferHostType、前端的 ipnet.js。三者可以各自漂移，而它们的结论直接影响入库类型与导出文本。

#### 1.4 测试套件可靠性（Node E2E Mock 套件）

##### Mock 与真实 libSQL REST API 的核心不一致

这是本次审查里价值最高的发现。Mock（tests/e2e.mjs）用 node:sqlite 落库，再把结果转成 columns 加 rows 的形状。对于 SELECT 它做对了，对于写语句它返回的是顶层 changes。

而 libSQL 的 HTTP 管道把受影响行数放在 results.rows_written 之下。后端代码里其实已经有人知道这件事：edit.js 有一个 statementChanges 辅助函数同时读两种形状，注释写得明明白白，即「直接读 changes 在真实 Turso 下恒为 undefined，会让 update/rename 误报记录不存在」。

问题是这个辅助函数只被用在 2 个地方，另外 11 处直接读顶层 results 里的 changes。在真实 Turso 上这些值全部是 undefined，求值后分别变成 0 或 false。受影响的位置包括删除、清空、清空空备注、批量导入的 updated 与 created 统计、降维的 deleted 与 created、订阅删除、prefs 删除计数，以及 recordHit 的 changed 标记。

测试全绿的原因正是：Mock 恰好满足了那个错误的形状。这个缺陷越过整条测试防线，直接命中生产。

##### 事务语义完全没有被模拟

请求体带了 serializable 标志，Mock 直接忽略它，逐条在自动提交模式下执行。后果是：

- Mock 里第 3 条语句失败时，前 2 条仍然留在库里；
- 生产上整个批次会回滚，前 2 条不会留下。

于是测试可以断言一个生产上永远不存在的中间状态，也可以反过来漏掉生产上真实存在的部分提交风险（见 1.1 节的三处跨批次原子性问题）。当前套件对降维排除和批量导入的事务边界实际上一无所知。

##### 零故障注入

没有 429、没有 5xx、没有超时、没有 rows_written-only 响应、没有超大批次拒绝。Turso 配额限流、写锁竞争、网络抖动这些真实世界的主要失败模式在当前套件里完全不可测。

##### 其他一致性缺口

- SQLite 与 libSQL 的差异：ensureMigrations 靠错误消息文本匹配来判断迁移是否已完成。libSQL 的报错措辞若与 SQLite 有差异，这条匹配会失效，迁移异常会直接在每一个请求上变成 500。
- globalThis.fetch 的整体替换：靠 127.0.0.1 前缀分流「数据库请求」与「订阅抓取」。任何非环回地址的本地 fetch 都会静默掉进「测试未登记的地址」分支，把一个真实的网络错误伪装成桩缺失。
- 证书与 TLS：需要宿主机有 openssl 生成自签证书，并且关闭整个进程的证书校验。在没有 openssl 的 CI 上会直接退出。
- 迁移路径几乎没被覆盖：migrationsApplied 是被测生产模块的模块级状态，一个进程内最多为真一次，而且只在某个用例恰好命中未迁移库时才会走到。迁移的重复调用幂等性实际上没有测试。

##### 覆盖面评价

解析、校验、导出格式化、边界条件的覆盖是充分且高质量的，LIKE 通配符转义、IP 字面量越界、DEVICE 策略大小写、路由覆盖都有专门用例。薄弱区精确地落在并发、失败、以及响应形状契约上，而前面所有的严重问题都住在那片区域。

### 2. 关键路径分析

#### 路径 A：Surge FINAL 命中上报到 surge_logs

流转：请求落入 FINAL，触发 SCRIPT 规则脚本，final-logger.js 从 persistentStore 读配置，post 到 /api/logger/hit（5 秒超时），CF Worker 校验上报令牌，recordHit，executeTursoBatch 提交单条 upsert，落到 Turso。

单点故障：

1. 单一 Turso 实例承担全系统读与写，无副本、无降级，是全系统唯一的硬单点。
2. persistentStore 配置链：面板未成功刷新过一次，上报即永久静默失败，且无任何提示。
3. 令牌变量缺失时全量 401。这是设计上的 fail-closed，但形态是硬开关，没有灰度空间。
4. 无重试、无队列、无补偿，任何单次失败即永久丢点。

延迟瓶颈：

1. 冷 isolate：迁移往返加业务往返，两次串行 TLS，且第一次是 schema 写。
2. 每次命中一次独立 TLS 握手加一个远端事务，无任何批量。
3. 热点主机名上重复写同一行，行级写竞争随 QPS 上升。
4. 客户端 5 秒超时是硬顶：服务端慢于 5 秒时客户端已放弃，服务端却可能仍在写入，两端对成功与否的判断不一致。

#### 路径 B：订阅解析导入

流转：面板调 /api/subscribe/parse，guard.js 做字面量黑名单校验，extract.js 的带重试抓取（单次 8 秒、最多 3 次、总预算 30 秒），extractRuleLines 提取规则行，必要时 base64 解码后重试一次，结果返回前端，用户点保存后 upsertSubscription，后续 /batch 走 batchOverride（merge 或 override），分块顺序提交。

单点故障：

1. 远端订阅源本身不可达或被限流。已有 3 次重试兜底，但没有第二源、也没有缓存之外的降级。
2. 抓取总预算是 30 秒，而面板侧请求有自己的超时。若前端超时短于 30 秒，会出现「前端已断开、后端还在抓」的孤儿请求，其结果无人消费。这一处需要前后端超时预算显式对齐。
3. 单一 Turso。

延迟瓶颈：

1. 30 秒总预算是面板最长的阻塞操作，期间用户只能转圈。
2. batchOverride 分块顺序提交：1500 行上限对应约 3000 条语句、约 15 个串行往返，不并行、无进度反馈。这是面板最慢的写路径。
3. base64 重试会让提取逻辑对同一份内容完整跑两遍，2MB 上限内容下 CPU 成本可观。
4. parseCache 是进程内 Map：200 条上限、5 分钟 TTL、多 isolate 不共享。命中率低且不可预测，重复点击重新解析时是否命中缓存取决于请求落到哪个 isolate。

#### 路径 C：过滤导出与订阅直链

流转：Surge 请求 /api/export（或面板请求 /api/logger/export），listPrefs 读全局筛选配置，buildExport，getAllLogs 全表无 LIMIT 读取，内存中做类型、来源、时间窗过滤并格式化，textResponse 返回。

单点故障：

1. 单一 Turso。导出是纯读，数据库不可用时订阅直链返回 500，Surge 侧表现为订阅更新失败，而规则集本身还是旧的，用户看到的是「订阅刷不出来」而不是「服务挂了」。
2. /api/export 依赖偏好表拿筛选条件。偏好表读失败会让整个导出失败，没有「读不到偏好就按无筛导出」的降级分支。
3. 无边缘缓存。Cache-Control 只对浏览器和 Surge 客户端有效，Function 响应本身没有被 CF 边缘缓存，每次订阅刷新都实打实打到 Turso。

延迟瓶颈：

1. getAllLogs 无 LIMIT 全表读全列。表到 5 万行时，单次导出等于一次数十兆的读取加全量字符串拼接。这是整条链路最陡的可扩展性悬崖。
2. buildExport 里 IPv 版本标记与规则格式化各自调用一次 IP 规范化逻辑，同一行被完整处理两轮。
3. reduceExclude 的 IP 分支对全表做无 LIMIT 查询。每次降维一次全表读。
4. getStats 一次批量 10 条语句是好的，但其中备注为空的计数条件必然全表扫描，索引帮不上忙。

## 二、优化建议（核心文档外部独立列出）

以下为拓展性方向，不在上表修复范围内，仅供思路参考。

1. Cloudflare Cache API 与 KV 做边缘缓存防护

给固定订阅导出与统计端点加一层 Cache API 缓存，采用 stale-while-revalidate 语义，把订阅直链与统计卡的读压力从 Turso 挪到边缘节点；写操作完成后按标签主动失效对应缓存。Turso 从此只承担真实写入与低频列表查询，读侧可用性也随边缘解耦。相比 KV，Cache API 无额外计费维度且支持主动清理，更适合这种「读多写少、允许短时陈旧」的形状。

2. 批量上报 Batch Pipeline 模式

新增一个接受数组的上报入口，用一次批量事务提交整组 upsert；同时改造 final-logger.js，在脚本内维护一个「主机名到待报次数」的内存窗口（例如 5 秒或满 20 条 flush），同一主机名在窗口内只发一次并附带增量。这把写 QPS 从每命中一次降到每窗口每主机名一次，是把命中采集从不可持续拉到可持续的关键一步，且对服务端是完全兼容的新增接口。

3. Web UI 轻量响应式封装

不起框架，只引入一个极小的信号层（Proxy 代理加显式渲染调度），把派生状态做成带记忆的 computed：可见列表、来源维度、统计卡。写操作后只重算受影响的切片，而不是全量刷新。配合来源维度改为只取去重值的查询，可以彻底去掉整份重复拉取，并把候选统计的多轮全量扫描降为一次预聚合。这是投入产出比最高的一项前端改造。

4. Turso 嵌入式副本与读写分离

把固定订阅导出与面板读取切到只读副本或嵌入式副本，让高频上报写不阻塞导出读，也让 Turso 单点从「读写同时失效」缩为「写侧失效可降级为只读服务」。配合导出链路的读写分离，全表读压力也能从主库上移走。

5. 可观测性与配额护栏

Workers 侧加基于 Cache API 或 Durable Object 的滑动窗口计数，按令牌维度给上报接口限流，挡住「令牌泄漏后被用来刷计数、污染表」的场景；Turso 失败时把待报数据暂存本地队列，下个窗口补报，把最多一次提升为至少一次。同时用日志推送把结构化事件外送，搭一个「应有对实收」的对账看板，这一项是把「上报丢失不可见」这个当前最大的运维盲区变成可观测指标的关键。
